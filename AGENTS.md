# Nyaymalaw build rules

The advocate's latest message is interpreted in the context of the whole saved
conversation and the current authorised work. Preserve the complete transcript.
Do not silently trim it, replace it with an uncheckable summary, or treat a
temporary change of subject as a change to the matter record.

For every new model prompt, state four things plainly: **Message** (the input
and its provenance), **Purpose** (the decision this call makes), **Look for**
(the evidence and distinctions the model should examine), and **Outcome** (the
exact output contract). Keep matter data in the variable input, outside the
stable instruction. Validate structured output and its references before use.
An interpretation is a proposal, never authority to change a fact, permission,
source status, or external action.

On every message, identify materially significant legal content against the
whole conversation. Preserve the exact current words, any earlier words needed
to understand them, their speaker, matter scope, attribution, uncertainty,
relation to prior content, and provisional importance. Keep these observations
as proposals attached to their source turn; do not silently turn them into
admitted facts or mix another matter into the current file.

Write general rules for relationships between messages, tasks, matters, and
evidence. Do not add keyword lists, sample-case branches, or parallel prompt
variants to approximate the range of legal situations. A model can describe
several requests in one message; the code must preserve them rather than force
one exclusive label. If context is incomplete or a reference is ambiguous,
make that visible and ask only for the distinction needed to proceed.

Keep one owner for each decision and one durable record for each fact. Reuse
the application's authenticated boundaries and storage contracts where they
fit; do not copy archived legal-brain or Agentified NM snippets without first
telling the user exactly what is proposed for reuse. Tests should exercise
unanticipated turns, corrections, diversions, return to prior work, missing
context, and mixed requests through the actual public boundary as it ships.

When a test, script, or browser run reveals a failure, identify the general
invariant that failed before editing code. Fix the invariant at its owning
boundary so the change applies to comparable matters and requests. Use the
observed case as a regression example, not as a condition, keyword, prompt
exception, or dispute-specific branch. Remove redundant paths rather than
layering another special case on top.

For every new or changed model flow, report the number of model calls per user
turn, including conditional calls, their purpose, and what input and output
each carries. Look for opportunities to combine decisions that genuinely share
context and quality requirements. Remove redundant calls, but retain separate
calls when evidence gathering, independent verification, or a distinct model
tier is necessary. Treat latency and token cost as design constraints and test
the call count at the service boundary.

Treat failures at the smallest independent unit. Preserve valid work, mark the
failed unit and any missing coverage explicitly, and retry it conditionally
without repeating already admitted user input. Never present a partial search
or analysis as complete. Stop the whole turn before saving when conversation
history, identity, attribution, source ownership, or commit integrity cannot
be trusted; saving an empty result for an unread stage would silently lose
material and is not graceful recovery.
