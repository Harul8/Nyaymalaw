## Item

26 Oct 2026, the usage check refusing under load, and how NM serves thousands of users

## Description

The owner: "how do we avoid this [the 503 'usage could not be checked'], this is an internal counter check without any model calls, so how come we are not able to manage this load? there will be 1000's of users in future, how do we manage it then? / while we are on this topic, how do we do load balancing to support 1000's of users and still make the servers available without any issues?". CLAUDE'S MEASUREMENT, 26 Oct 2026, on throwaway files: a usage check costs about 0.6 ms alone; 16 callers at once got about 530 checks a second (125 a second with the disk kept busy), with none refused in about 1,600 checks, the slowest few percent taking 1-4 s. THE CAUSE OF THE 503 IS NOT LOAD: it is the first use of a store file that does not exist yet when callers arrive together - one creates the file, another finds it still empty, takes it for a damaged store and refuses (12 of 600 callers in the test; 'the usage store has a schema it did not make'), and a fresh test store's first turn starts several model steps at once. The live store exists already, so it cannot happen there; the turn-attempt store has the same shape. The store also dropped the real reason from its refusal, so the log could not say. FIX: AN.24. THE LIMITS TO THOUSANDS OF USERS ARE ELSEWHERE: every request that waits on the model, a turn above all, holds one of the web framework's 40 worker threads for its whole length (minutes), so about 40 turns at once per process and everything else queues; each turn rewrites its whole conversation file (the biggest is 29 MB); the AI provider's rate limits and cost; and NM is built as a ONE-SERVER SYSTEM - matters, keys, accounts, sessions, usage, turn claims, locks, uploads and in-memory progress and caches are local - so a load balancer in front of two copies would give each its own allowance counts, sessions and matters. PROPOSED PATH (for the owner's calls): (1) pilot, a few hundred users: one well-run server in an Indian cloud region, backups, monitoring, a standby, the fixes above; (2) move state out first: managed PostgreSQL for accounts, sessions, usage, claims and conversations (one row per turn, sealed under the matter's key, so nothing rewrites a 29 MB file and paging is native), object storage for sealed documents and uploads, a cloud key service for the key-encrypting key, database locks instead of lock files; (3) stateless app servers (two or more, in different zones) behind a managed load balancer with health checks, connection draining and autoscaling, with turns run by a job queue and its own workers so the web servers stay responsive, progress and usage in shared storage, per-account limits and backoff protecting the provider's quota; (4) operate: dashboards and alerts, a load test at three times the expected peak, restore drills, data kept in an Indian region. CALLS PUT TO THE OWNER: (a) build the first-use fix now (answered by the owner's question; building); (b) write the scale-out path on the plan as staged work without building it (recorded here); (c) the pilot on one well-run server in an Indian cloud region with the move to shared services before any second server - owner to confirm or name a hosting preference and budget; (d) PostgreSQL, object storage and a cloud key service for the long term - owner to confirm; and the target number of users and date, so the stages can be sized.
