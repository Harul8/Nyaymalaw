DECISIONS (D116-D120, D122-D123 and D125 follow the owner's words; D121, D124 and D126-D128 are Claude's, for the owner to correct).
D116. ADMINS CHANGE THINGS IN THE APP (the owner: ok with the recommendation). This reverses O24's 'no HTTP endpoint exposes' for admins only. Every change asks for the admin's password again (good for 10 minutes), a reason of at most 200 characters, passes the CSRF and origin checks every unsafe route passes, and is made and written to the audit log in one step, or neither. An Admin (view only) is refused every change. The command-line tools stay and still work.
D117. WHO IS AN ADMIN (the owner: ok). The server's settings name them, NM_ADMINS="email:admin,email:view-only", read at start. Never a field on an account file, never settable over HTTP, never from the Admin pages. An entry whose level is not one of the two is ignored (a typo locks someone out; it can never raise anyone) and counted for the diagnostics. For anyone not named, every admin address answers 404 as if it did not exist, and the person menu does not show Admin.
D118. THREE ACCESS LEVELS (the owner, 7 Nov): Advocate, Admin, Admin (view only). Everyone not named in D117 is an Advocate. Professional approval (with its date), an email not yet confirmed, and a suspension are shown BESIDE the level as facts of the account, never as levels of their own. An email still waiting to be confirmed has no account yet, so it appears in its own list.
D119. WHAT AN ADMIN SEES (the owner, 7 Nov): usage statistics, balance available and consumption, with the account facts they belong to - name, email, enrolment number, firm, level, professional approval and its end date, AI data sharing on or off, last sign-in, live sessions and their device labels, when the account was made. NEVER conversations, matters, the board, documents or files, answers, research notes, advice preferences, dictation, or anything an advocate wrote or saved. Kept true structurally: every Admin payload is built from named allowed fields (never by removing fields from a fuller record), and a test fails if a forbidden key, or any text of a saved matter, appears in any Admin response. Showing an account's usage beside its email is within the owner's words; whether the usage and privacy notices say so is the owner's to review (not legal sign-off).
D120. THE TURN RECORD (the owner: yes, add it). One content-free line when a turn ends: the account's digest, when it started and ended, seconds, how it ended (answered; stopped by the advocate; refused - a sign-in that ended, AI sharing off, an allowance used up, an earlier answer still being worked on, a document it could not use; failed - NM's side or the AI service's), the model and effort chosen, the number of model calls, the cost, and the number of documents sent (a number only). No conversation or matter identity, no words. Written by the application where a turn ends (composition.run_turn); a failure to write it is logged and never fails or delays a turn. It lives in its own sidecar store (turn-events.sqlite), so usage.sqlite's strict schema is not changed. Until it exists the answers-per-day and time-per-answer figures read 'needs the turn record'.
D121. SUSPEND AN ACCOUNT (not answered separately; the design carries it; built last). New: an account flag, set by an Admin with the password and a reason, that refuses sign-in and ends the account's sessions; the matters are untouched; reversible.
D122. APPEND, NOT REBUILD (the owner: ok). Only the new documents are turned into vectors. The new index file is the old file's vectors plus the new ones; the passage rows are appended at the next positions; the word index is rebuilt (the library is immutable once built); the lineage record and its verified block are updated; the earlier index, rows and record are kept beside it for roll-back. Nothing is re-encoded. It becomes live at one planned restart, before the index opens (the index is memory-mapped on Windows and cannot be replaced while the server runs), and only when no turn is running. Delta segments searched alongside the main set (a true in-place append) are NOT built; they are revisited only if additions become frequent.
D123. WHAT CAN BE ADDED (the owner: ok). Acts and judgments as plain text in the library's raw form. PDF and web-page conversion later. A document already held (an Act by name and year; a judgment by citation or by identity) is refused, not replaced. An Admin approves each batch after the check, and the approval is attributed in the audit log, because which Acts the product covers is the owner's decision. Judgments of the Andhra Pradesh High Court are held as the High Court of Telangana's with the court as filed kept (AN.45, D92, D111). No paid model call is part of ingestion; naming a new judgment's paragraph kinds stays the separate, spend-limited job of AN.45 (D115).
D124. THE PAGE (Claude's). The Admin area is its own page, opened from one new entry in the person menu that only admins see. The workspace's board and reading pane are not touched (D60). Its files are declared in nm/source_layout.json's closed asset list and its modules in the layout with the expected_roles counts raised.
D125. THE JUDGMENT READ STAGE (the owner, mid-turn). Only the READ stage was started, on 7 Nov 2026 (3 workers, about 12 minutes; nothing live touched, the output a new 2.4 GB folder, legal_database/vector_store/judgments_v3). The index stage (about 3.7 hours on the card) and the swap (server stopped) are NOT authorised. The aliases were not checked, so the 106,049 section references stay unresolved; checking pipeline/act_aliases.json (59 entries, all unchecked) and re-running the read stage (12 minutes) before the index stage is advised if the aliases are to count.
D126. THE AUDIT (Claude's). Append-only, in a new sidecar admin.sqlite: each entry holds the time, the acting admin, what was done, the target (an account's email or a batch), the reason, how it ended, and a fingerprint that includes the previous entry's - so a removed or changed entry shows. Tamper-evident, not tamper-proof: anyone with the server's files can rewrite them, and the page says so. No message, document or answer text can be written to it.
D127. BUILT IN A COPY, APPLIED ON THE WORD (Claude's, as AN.45 D113 and the standing rule). Built in a scratch copy of the tree, published piece by piece (one production file and no more than one prompt each; there is no prompt here), and nothing of nm/, tests/ or pipeline/ is applied to the owner's server until the owner says so.
D128. WHAT THE ADMIN AREA NEVER DOES (Claude's). No model call, no paid work, no corpus change without a check, an Admin's approval and the planned restart. A failure of one of its views shows that view as unavailable and never fails another or the workspace.
