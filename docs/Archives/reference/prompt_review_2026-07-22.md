# Nyaymalaw Prompt And Prompt-Logic Review

Date: 2026-07-22

Scope reviewed:
- Current local workspace state, including uncommitted offline changes.
- Runtime prompts, rewrite prompts, structured-output prompts, evaluator prompts, and the logic that decides when each prompt is used.
- Prompt-bearing files in `agents/`, `retrieval/`, `prompts/`, `api/`, `infra/`, and the drafting/document subflows.

Method:
- I first mapped the codebase structure with the code graph, then read only the prompt-bearing files and the control paths that materially change prompt behavior, grounding, or cost.
- I treated "prompt quality" as a joint question of output quality, legal reliability, instruction conflict, determinism, and token/latency cost.

## Executive view

The system already has several strong traits that many legal AI products never reach:
- It does not rely on one prompt alone. It combines retrieval, settled-charge logic, authority-floor checks, structured turns, and deterministic post-validation.
- It is visibly trying to enforce legal grounding rather than merely asking the model to "be accurate."
- The advocate-mode direction is materially better than a generic legal chatbot because it explicitly tries to reason in peer register, not lay-client register.

The main weaknesses are architectural rather than stylistic:
- The consult path is still too prompt-heavy and too serial. One user turn can trigger planning, issue spotting, charge resolution, checklist refresh, main answer generation, then multiple repair rewrites. That improves safety, but it also raises cost, latency, and instruction interference.
- The biggest prompt `_CONSULT_PROMPT` is overloaded. It contains identity, tone, safety, multilingual behavior, corpus-scope policy, intake flow, output policy, and stage behavior all at once. That is a classic "too many active objectives in one context window" design.
- Prompt assets are split across two architectures: older prompt modules in `prompts/` and newer logic embedded in `agents/*`. Some are active, some are partially wired, and at least one import path appears inconsistent.

Recommended direction:
- Keep the deterministic legal guards.
- Shrink the large prompts.
- Move more behavior into structured slots and deterministic composition.
- Reduce the number of repair passes by making the first generated answer more constrained and evidence-bound.
- Create an explicit prompt registry with status: active, dormant, experimental, deprecated.

## Highest-priority improvements

1. Shrink and modularize the consult stack.
   Basis: the current consult behavior is carried by one mega-prompt plus several repair prompts. That is expensive and prone to instruction conflict.

2. Move more first-pass generation to structured intermediate objects.
   Basis: the strongest parts of the system already do this (`call_structured_llm`, narrow intake turns, settled charges). Those parts are more stable than freeform prose plus repair.

3. Reduce duplicate prompt surfaces.
   Basis: the repo currently has parallel intake and research prompt assets, multiple query-normalization surfaces, and duplicated sufficiency logic. That increases maintenance risk and token spend.

4. Treat prompt governance as architecture, not copywriting.
   Basis: the main issues are ownership, activation status, repair frequency, and sequencing, not whether a sentence could be worded more elegantly.

5. Keep the deterministic legal safety rails.
   Basis: the authority-floor checks, act-section matching, repeal checks, and final end-of-chain gate are among the best reliability mechanisms in the codebase. They should be preserved while the prompt stack is simplified.

## Bottom line

Nyaymalaw is not suffering from "weak prompts" in the usual sense. It already has several strong legal-AI prompt designs. The bigger problem is prompt-system complexity: too many prompt surfaces, too much policy duplication, and too many serial repairs after generation.

If I were prioritizing the next wave of improvement, I would not start by rewriting lots of wording. I would start by:
- reducing the consult mega-prompt,
- consolidating duplicate helper prompts,
- making more of the answer pipeline structured before prose,
- and adding a prompt registry so the team knows which prompts are truly production-critical.

That would improve output quality, lower cost, and make the system much easier to reason about as it scales.
